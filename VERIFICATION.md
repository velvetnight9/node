# Проверка установщиков 2026-10-19.3

Проверка выполнена в отдельной локальной Linux VM. Боевые ноды в ходе этой
проверки не изменялись. ОС тестового окружения — Debian 12 с systemd; сетевые
пространства имён, UFW, nftables, Fail2ban, sshd, nginx и TLS работают реально.

## Проверяемые сценарии

- Управляющий TCP-порт разрешён панели по IPv4/IPv6; другие источники закрыты.
- Старые публичные разрешения controlport, 3000 и 3001 удаляются с учётом
  работающих сервисов. Фактические SSH-порты сохраняются.
- Публичный Xray TCP/24443 автоматически разрешается. Loopback XHTTP/7443
  не получает публичного правила; внутренние API-порты исключены.
- Непривилегированный процесс с поддельным именем rw-core не получает
  автоматического разрешения; root-owned listener определяется по данным ss.
- Повторная донастройка не создаёт дубликатов. Смена IP панели закрывает старый IP.
- Ранний UFW ACCEPT и DNAT опубликованного порта не обходят ограничение панели.
- Fail2ban блокирует SSH по IPv4/IPv6, сохраняя доступ к другому TCP-сервису.
- Ошибочная новая конфигурация nftables возвращает предыдущие правила и доступ.
- Стандартный `install.sh --repair` проходит путь донастройки без полной установки.
- Для обоих CDN исправляется nginx upstream 4443 → фактически слушающий 7443:
  HTTPS-ответ меняется с 502 на ответ backend 400. Повтор сохраняет конфигурацию.
- Собственный HTTP bootstrap после прерванного получения сертификата можно
  продолжить без переустановки существующей ноды.
- Поддельный тег sshd в journal не подтверждает вход по ключу. Настоящий вход
  по ключу подтверждается по SSH-предкам процесса и доверенным полям journal;
  после этого парольный вход отключается без переноса SSH-порта.
- Системный nginx получает минимум 8192 worker_connections и 65535 nofile;
  повтор не изменяет файлы, уже имеющие нужные значения.
- Проходят прежние проверки вывода установщика, обработки ошибок apt,
  маскирования секретов в логе и определения остаточного SSH listener.

`tests/check_sources.py` проверяет Bash-синтаксис, встроенный Python, сборку общей
защиты во все три файла, неоднозначные upstream и обнаружение TCP/UDP Xray.

## Границы результата

Docker API существующей RemnaWave-ноды в CDN-тесте заменён контролируемым
ответом, чтобы проверить запрет случайного пересоздания. Backend в тесте —
локальный HTTP-сервер с именем процесса rw-core, не настоящий VLESS-туннель.
Сценарий продолжения ACME использует тестовый сертификат и подмену Certbot.
Тест DNAT проверяет реальные Linux NAT/FORWARD правила с отдельным backend,
а не полную установку RemnaWave-контейнера с настоящим SECRET_KEY.

Полная новая установка с реальным доменом/панелью, выпуск Let's Encrypt,
Ubuntu 24.04, аккаунты Timeweb/Яндекс CDN, LTE и скорость пользовательского
туннеля здесь не проверялись. Ответ origin 400/404 сам по себе не доказывает
работоспособность публичного CDN. После установки нужны проверка Online в
панели, обновление подписки и реальный upload/download через CDN.

Не запускайте `tests/linux-*.sh` на рабочей машине: они создают тестовые
интерфейсы, изменяют firewall и конфигурацию тестовых служб.
